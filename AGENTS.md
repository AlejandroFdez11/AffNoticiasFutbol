# AFFutbol — agent guide

## Repo shape

- The Expo app lives in `AFFutbol/`; the repo root is just the wrapper around that folder, `README.md`, and this file. Run npm/Expo commands from `AFFutbol/`.
- One npm package (`AFFutbol/package.json` + `package-lock.json`); no workspaces and no bun/pnpm/yarn. Use `npm`/`npx`.
- `README.md` is the product/roadmap source of truth; update it when a phase changes.
- All `src/...` paths below are relative to `AFFutbol/`.
- Day-to-day work happens on the `develop` branch; `main` is only updated on release. Never commit `.env`.

## Setup and verification (from `AFFutbol/`)

```bash
npm install
Copy-Item .env.example .env   # PowerShell; use cp on macOS/Linux
npx expo start                # Expo Go covers everything except push (needs a dev build)
npx expo start -c             # clear the cache after editing .env
npm run lint
npm run typecheck
npm test -- --ci              # full suite
npm test -- format-test       # single test file
npx expo-doctor               # dependency/config health
```

- Use `npx expo install <pkg>` (not `npm install <pkg>`) for Expo/React Native packages so versions match SDK 58. `npx expo install --fix` repairs mismatches.
- There is no CI workflow. Lint, typecheck, and tests are the gate; run them before declaring work done.
- Jest is configured in `package.json` (`jest-expo`, `@/` and `@/assets/` aliases). Tests live next to the code in `__tests__/` folders, e.g. `src/lib/__tests__/format-test.ts`, `src/features/auth/__tests__/validation-test.ts`.
- Optional bundle smoke test without a simulator: `npx expo export --platform ios` or `--platform web`.

## Expo version discipline

- Expo SDK 58, React Native 0.88, React 19.3, TypeScript strict. Expo APIs change every SDK; verify against `https://docs.expo.dev/versions/v58.0.0/` and `https://docs.expo.dev/llms.txt`, not memory.
- `ios/` and `android/` are generated by CNG and gitignored. Never create or edit them by hand; configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. Adding native code requires a development build: `expo-dev-client` is installed and `eas.json` has a `development` profile, so build with `npx eas-cli build --profile development` before testing push or Apple Sign In.

## Routing and tabs

- Routes live in `src/app/`; `_layout.tsx` files define navigators. The root `Stack` is `src/app/_layout.tsx`; the tab group is `src/app/(tabs)/`. Keep non-route code outside `src/app/`.
- Stacked routes outside the tabs: `match/[id]` (match detail), `article/[id]` (news or rumour detail), `statistics` (standings/scorers), and the account routes `auth`, `auth-callback`, `reset-password` and `edit-profile`. `auth`, `reset-password` and `edit-profile` open as modals. Register new stacked routes in the root `Stack`.
- Tabs are `index` (Partidos), `news` (Noticias), `predictions` (Predicciones), `rankings` (Ranking), and `profile` (Perfil). Trigger names must match the route filenames.
- Native tabs: `src/components/app-tabs.tsx` uses `expo-router/native-tabs` (SDK 58 name, not `unstable-native-tabs`). Icons use `sf` for iOS and `md` Material Symbols for Android.
- Web has a separate headless tab bar: `src/components/app-tabs.web.tsx` (`expo-router/ui`, `TABS` array). Any tab add/rename/reorder must be done in both files.
- Typed routes are generated in `.expo/types/router.d.ts` (gitignored). After adding or moving a route, run `npx expo start` once (then stop it) to regenerate, then `npm run typecheck`; stale types cause `Href` errors.

## UI and theme

- Design tokens live in `src/constants/theme.ts` (`Colors`, `Spacing`, `Radii`, `Brand`, `MaxContentWidth`). Every color key must exist in both `light` and `dark`; `ThemeColor` is the intersection of the two palettes.
- Use `useTheme()`, `ThemedText`, and `ThemedView`; do not hardcode palette hex values in screens (the Google "G" badge in `oauth-buttons.tsx` is the only brand-mandated exception). Navigation themes live in `src/constants/navigation-theme.ts`.
- Reuse the shared components in `src/components/` before creating new ones: `Button` (variants `primary`/`secondary`/`ghost`, `loading`, `disabled`), `IconButton`, `TextField`, `SegmentedControl`, `Avatar`, `TeamBadge`, `StateCard`, `ScreenHeader`, `BrandMark`.
- Standalone icons use `SymbolView` (`expo-symbols`) with `name={{ ios, android, web }}`: SF Symbols on iOS, Material Symbols on Android/web.
- `Screen` (`src/components/screen.tsx`) handles safe area, scrolling, and max width. Use `ScreenHeader` for page headers and `PlaceholderScreen` for unfinished sections.
- UI copy is Spanish; code identifiers and comments are English.
- `StyleSheet.absoluteFillObject` is absent from RN 0.88 types; use explicit `position: 'absolute'` plus edges (see `src/components/animated-splash.tsx`).

## Data and environment

- Football data comes from API-Football (`https://v3.football.api-sports.io`). The client lives in `src/services/api-football/` (typed errors, mock dataset in `mocks-data.ts`) and the query hooks, mappers and components in `src/features/matches/`. Keep API calls out of route files.
- The current API-Football plan is **Free**: 100 requests/day, `fixtures?date=` / `fixtures?id=` only (league+season queries outside 2022–2024 are rejected). Do not add automatic polling; the matches screen refreshes manually.
- The matches feed is filtered on the device to the curated competition allowlist in `src/features/matches/league-filter.ts`. Filtering costs no extra requests; do not fetch competitions one by one on the Free plan.
- News and transfer rumours are real and live in Supabase: the `news-refresh` Edge Function (`supabase/functions/news-refresh/`) pulls Spanish RSS feeds listed in the `news_sources` table, normalises them with `supabase/functions/_shared/normalize.ts` (pure functions, no Deno globals, covered by Jest) and upserts into `news_items`. The app only reads that table through `src/features/news/api.ts`; `src/features/news/data.ts` is a dev fallback used when Supabase is not configured. Store and show only headline, excerpt, image and a link to the outlet — never the article body. Deploy with `npx supabase functions deploy news-refresh`.
- Statistics are still **curated local sample data** (`src/features/statistics/data.ts`), labelled as sample in the UI. Do not present sample standings as real; replace the query functions in `src/features/statistics/api.ts` without changing screen props.
- Server state uses TanStack Query (`src/lib/query-client.ts`). Dates use date-fns with the `es` locale (`src/lib/format.ts`); do not add dayjs/moment.
- `EXPO_PUBLIC_*` values must be read with static dot notation (`process.env.EXPO_PUBLIC_X`) to be inlined; see `src/lib/env.ts`. A misspelled variable name fails silently as `undefined`.
- Mocks default to on when no API key is set; `EXPO_PUBLIC_USE_MOCKS=true|false` overrides that. `.env` is gitignored; `.env.example` is the template. Never commit a real key.
- `EXPO_PUBLIC_*` is bundled and public. Before publishing, API-Football calls must move behind a Supabase Edge Function (not built yet).

## Supabase, auth and profiles (Phase 3)

- Env vars: `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` (`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is accepted as a fallback; see `src/lib/env.ts`). Both are public. Never put the `service_role`/secret key in the app or in `.env`.
- The single Supabase client lives in `src/features/auth/supabase.ts` and is `null` when env vars are missing, so the football screens still boot. Always obtain it through `requireSupabase()`; do not call `createClient` anywhere else (a second client causes "Multiple GoTrueClient" warnings and inconsistent sessions).
- Session storage: native uses `expo-secure-store` with chunking (`src/features/auth/storage.ts`, values are split because Keychain rejects large values); web uses `localStorage` with an in-memory fallback (`storage.web.ts`). Auth flow is PKCE with `detectSessionInUrl: false`; the code is exchanged explicitly in `completeAuthFromUrl`.
- Auth state comes only from `useAuth()` in `src/features/auth/auth-context.tsx` (`status`, `session`, `user`, `profile`, `signIn`, `signUp`, `signInWithGoogle`, `signInWithApple`, `signOut`, `requestPasswordReset`, `updatePassword`, `completeAuthFromUrl`, `updateProfile`, `refreshProfile`). Do not add a second provider or a parallel session hook.
- The app is usable without an account: Partidos, Noticias and Estadísticas never require a session. Predicciones, Ranking and Perfil must check `useAuth().status` and send signed-out users to `/auth`.
- `/auth-callback` is the single deep-link target for OAuth, email confirmation and password recovery. Build the URL only with `getAuthRedirectUrl()` (`Linking.createURL('auth-callback')`). Redirect URLs must be allowed in Supabase → Authentication → URL Configuration: `exp://**` for Expo Go (development only, remove before release) and `affutbol://**` for builds (`scheme` is `affutbol` in `app.json`).
- Google: browser OAuth through `supabase.auth.signInWithOAuth` + `expo-web-browser`; works in Expo Go. Requires a **Web application** OAuth client in Google Cloud whose authorized redirect URI is `https://<project-ref>.supabase.co/auth/v1/callback`, and both Client ID **and Client Secret** saved in the Supabase Google provider. While the Google consent screen is in Testing, only listed test users can sign in.
- Apple: the code path exists (`signInWithApple`, `expo-apple-authentication`, `usesAppleSignIn` in `app.json`) but it needs a paid Apple Developer account and a development build with bundle id `com.alejandroff.affutbol`. Treat it as untested; do not claim it works in Expo Go.
- Database: SQL migrations live in `supabase/migrations/` (run in the Supabase SQL editor or `supabase db push`). Do not commit empty migration files. `public.profiles` is 1:1 with `auth.users` (`id` is the user id) with `display_name`, `username` (unique, `^[a-z0-9._]{3,20}$`), `favorite_team_id/name/logo`, `avatar_url`, timestamps. RLS is on: anyone can read, users can insert/update only their own row. The `handle_new_user` trigger creates the row on sign-up; `fetchProfile` also creates it if missing.
- Profile code is in `src/features/profile/`: `types.ts` maps snake_case rows to camelCase (`mapProfile`), `api.ts` does the queries, `validation.ts` validates usernames. The favourite-team picker uses the local `TEAM_OPTIONS` list in `teams.ts` (IDs match API-Football, so it costs no requests).
- Every new table must ship with RLS enabled and explicit policies in the same migration. Never rely on the client to enforce ownership.
- Not built yet: multiple profiles per account (the Netflix-style picker is a design reference, the model is one profile per account), following several teams (needs its own table), avatar upload.

## Predictions (Phase 4)

- Scoring rules: exact score = 10 points; correct goals for only one team = 5 points; otherwise 0. They live in `public.prediction_points()` and are mirrored read-only in `src/features/predictions/scoring.ts`.
- Predictions are for the user's favourite team's matches. The client can only insert/update `home_goals` and `away_goals` before kickoff: `public.predictions` RLS + column grants reject writes to `status`, `points`, `settled_at` and the final-score columns. Never let the app compute and store points.
- Settlement runs server-side: `supabase/functions/settle-predictions/` asks API-Football for each pending fixture (`fixtures?id=`, batch capped at 20), then calls `settle_fixture()` or `void_fixture()` as the service role. `_shared/settle.ts` holds the pure decision logic and is covered by Jest. The cron job in `20261107000000_settle_cron.sql` calls it every 30 minutes with the secret stored in Supabase Vault (`settle_secret`, same value as `PREDICTIONS_SETTLE_SECRET`).
- Client code is in `src/features/predictions/`: `api.ts` (queries/mutations), `fixtures.ts` (kickoff window), `scoring.ts` (summary/outcome copy), plus the screen components. The match list reuses the matches query cache, so opening Predicciones costs no extra API-Football requests. The fixture date window is `PREDICTION_WINDOW_DAYS`.
- `settle_fixture` stores `final_home_goals`/`final_away_goals` with the prediction so the history never needs another API request. Voided matches keep `points = null`.

## Rankings and private leagues (Phase 5)

- Database: `public.leagues` (name, unique 6-character `invite_code`, `owner_id`) and `public.league_members` (PK `league_id, user_id`, `role` owner/member). Both have RLS: only members can read a league and its member list. There are no direct insert/delete grants.
- Writes go through `SECURITY DEFINER` RPCs in `20261108000000_leagues_rankings.sql`: `create_league(p_name)`, `join_league(p_code)`, `leave_league(p_league_id)` and `my_leagues()`. The owner leaving deletes the league. Invite codes are generated server-side (`generate_invite_code()`, alphabet without O/0/I/1) and must never be enumerated by the client.
- Leaderboards are aggregates computed in SQL, never by exposing predictions: `global_ranking(p_limit)` (users with at least one prediction, top N plus the caller's own row) and `league_ranking(p_league_id)` (every member, including members with 0 points, guarded by `is_league_member()`). Both return points/counters only and are executable by `authenticated` only.
- Client code is in `src/features/rankings/`: `types.ts` (snake_case rows + bigint-to-number mapping), `validation.ts` (league name and invite code), `api.ts` (TanStack Query hooks and error copy) and `components/`. The Ranking tab has two scopes: `Mundial` and `Mis ligas`. The profile summary reuses `useGlobalRanking()` to show the user's position.
- Any new leaderboard column must be added to both SQL functions and `RankingRow`/`RankingEntry`; keep the SQL aggregate and the client copy of it in sync. No API-Football requests are involved in rankings.
- Not built yet: public/discoverable leagues, per-league seasons or resets, roles beyond owner/member, push notifications for league invites.

## Push notifications (Phase 6)

- Three kinds, all sent from the backend: match reminder (~1 h before kickoff of the favourite team's matches, predicted or not), settled-prediction result, and ranking change (global + private leagues). The app never sends notifications; it only registers the device and stores preferences.
- Database (`20261109000000_push_notifications.sql`): `push_tokens` (one row per device token, `user_id` nullable until claimed), `notification_preferences` (1:1 with the user, three booleans, all true by default), `push_deliveries` (dedupe log with unique `dedupe_key`), `fixtures` (server-side cache of the day's fixtures) and `ranking_state` (last known position per scope and user). RLS everywhere: clients only read/write their own rows.
- Writes go through the `SECURITY DEFINER` RPCs `register_push_token(p_token, p_platform, p_device_name, p_app_version)` and `unregister_push_token(p_token)`. A device can change accounts, so the token is reassigned instead of duplicated. Never insert into `push_tokens` directly and never expose a token to another user.
- `ranking_positions()` is service-role only (`postgres` + `service_role`): it returns `scope_key` (`global` or `league:<uuid>`), `user_id` and `"position"` for every user. It is separate on purpose — `global_ranking()`/`league_ranking()` are per-caller. Keep its `order by` in sync with theirs, and keep `"position"` quoted (reserved word).
- Backend: `supabase/functions/send-push/` accepts `{ job: 'reminders' | 'results' | 'rankings' | 'sync-fixtures' | 'all', dryRun?: boolean }`, batches 100 messages per Expo call, deletes tokens Expo reports as `DeviceNotRegistered` and logs every send in `push_deliveries`. Pure logic lives in `_shared/notifications.ts` (copy, 60 ± 10 min window, dedupe keys, ticket parsing) and `_shared/fixture-cache.ts`, both covered by Jest. Deploy with `npx supabase functions deploy send-push --no-verify-jwt` (`verify_jwt = false` in `supabase/config.toml`).
- `20261109000100_push_cron.sql` schedules four pg_cron jobs: `push-reminders` (*/10), `push-results` (*/15), `push-rankings` (hourly at :07) and `push-sync-fixtures` (04:20 UTC). They authenticate with the `x-notify-secret` header, whose value lives in Supabase Vault as `notify_secret` and must equal the `PUSH_NOTIFY_SECRET` function secret. `sync-fixtures` is the only job that calls API-Football (2 requests/day) and it warms the `fixtures` table that reminders read.
- Ranking alerts are throttled to one per scope every 6 h and deduped by `<scope>|<position>|<yyyy-mm-dd>`; the first observation only records state, so nobody gets an alert for signing up.
- Client code is in `src/features/notifications/`: `permissions.ts` (`expo-notifications` wrapper, `getExpoProjectId()`), `device.ts` (stored token, enable/disable, `releaseStoredPushToken()`, `syncStoredPushToken()`), `api.ts` (TanStack hooks and error copy), `routes.ts` (allowlist of deep links), `notification-bridge.tsx` (handler plus tap routing, mounted in the root layout) and `components/notifications-card.tsx` (Perfil UI). `notification-bridge.web.tsx` is a no-op.
- `signOut` releases the push token before signing out (`src/features/auth/auth-context.tsx`), so the next account on the same phone does not inherit notifications.
- Tokens need the EAS project id: `eas init` writes `extra.eas.projectId` into `app.json`; `EXPO_PUBLIC_EAS_PROJECT_ID` is the fallback (`src/lib/env.ts`).
- Push does not work in Expo Go (from SDK 53) nor on web; it needs a development build or an installed build.

## EAS

- `eas.json` defines `development` (developmentClient, internal distribution, Android APK, channel `development`), `preview` and `production`. `expo-dev-client` is installed: build once with `npx eas-cli build --profile development` and run the app with `npx expo start --dev-client`. Push notifications and Apple Sign In need this build, not Expo Go.
- `npx eas-cli init` creates the EAS project and writes `extra.eas.projectId` into `app.json`; `getExpoPushTokenAsync()` returns nothing without it. Android push needs FCM credentials (EAS uploads `google-services.json`) and iOS needs an APNs key uploaded to EAS.
- Use `npx eas-cli@latest ...`; no global EAS CLI is assumed.
